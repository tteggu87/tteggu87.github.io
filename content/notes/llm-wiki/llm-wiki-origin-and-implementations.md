질문할 때마다 수백 페이지 원문에서 문맥을 긁어와 답하고는 이내 지워버리는 검색을 언제까지 반복해야 할까요? 안드레이 카파시(Andrej Karpathy)가 제시한 `LLM Wiki`는 답변 순간에 소멸하던 지식을 서로 연결된 Markdown 문서로 축적해 나가는 지속 가능한 지식 성장 루프입니다.

> [!summary] 핵심 결론
> RAG가 질문이 들어온 순간 관련 원문 조각을 찾아 일회성 답변을 만드는 방식이라면, LLM Wiki는 그 과정에서 얻은 데이터·반례·연결을 재사용 가능한 Markdown 파일로 남기는 지식 축적 시스템입니다. RAG보다 무조건 빠르거나 정확해서가 아니라, 사람이 언제든 직접 검토해 고칠 수 있고 에이전트가 함께 확장해 나가는 **편집 가능한 정본 지식고**라는 점에 핵심 가치가 있습니다.

## 1. 왜 원문 구상부터 읽어야 하는가

안드레이 카파시의 Gist 제목은 `LLM Wiki`이며, 특정 상용 프로그램의 가이드북이 아니라 **LLM을 활용해 개인 지식 기반을 아키텍처화하는 패턴**입니다. 카파시는 이를 완성된 제품 명세가 아닌, 자신의 에이전트에 직접 복사해 넣어 기본 행동을 지시하는 설정 파일 형태로 공유했습니다.

카파시의 원본 구상은 큰 아키텍처 방향을 제시할 뿐, 특정 기술 스택을 고정하지 않습니다.

- 특정 브랜드의 데이터베이스나 전용 저장소
- 고정된 임베딩 모델이나 벡터 검색 파이프라인
- 엄격하게 규격화된 폴더 구조와 frontmatter 속성
- Obsidian 이외의 전용 UI나 특정 앱
- 파이프라인 자동화 수준과 인간의 승인 절차

시중에 나온 개별 구현체부터 접하면 특정 도구의 부가 기능이 LLM Wiki의 본질처럼 오인될 수 있습니다. 따라서 원문이 명시한 최소 핵심 규약과 후속 구현체들이 덧붙인 확장 레이어를 명확히 구별해서 읽어야 합니다.

## 2. 검색 위치가 아닌 지식 수명의 전환

기존 RAG는 질문이 입력되는 순간 원문 DB를 조회하고 필요한 문맥 조각을 새로 조합해 응답을 생성합니다. 현재 질문의 즉각적인 근거를 찾기에는 유용하지만, 그 답을 도출하며 만들어진 맥락과 통찰은 답변 종료와 함께 사라집니다. 다음 질의 시 동일한 탐색 과정을 처음부터 다시 밟아야 합니다.

LLM Wiki가 지향하는 수명주기는 다릅니다.

```text
RAG:         질문 → 원문 검색 → 답변 생성 (소멸)

LLM Wiki:    새 원문 → Wiki 갱신 → 질문 → 답변 생성
                                      ↘ 통찰을 다시 Wiki 문서로 저장
```

여기서 LLM은 단순 텍스트 요약기에 머물지 않습니다. 신규 자료를 분석하고 기존 노트를 참조하며, 개념·인물·비교·종합을 업데이트하는 **지식 유지 관리자(Maintainer)**로 동작합니다.

사람과 LLM의 역할도 정교하게 갈라집니다.

- 사람은 읽을 원자료를 선별하고, 검증할 핵심 질문과 연구 방향을 설정합니다.
- LLM은 원문을 요약하고, 기존 페이지를 갱신하며, 문서 간 양방향 링크와 색인·로그를 보존합니다.
- 사람은 Obsidian 등 텍스트 뷰어로 정돈된 지식 연결망을 검토하고 오개념을 교정합니다.

결국 LLM Wiki의 본질은 "더 정교한 검색 파이프라인"을 만드는 데 있지 않습니다. **단발성 대화로 휘발될 분석 결과를 다음 작업에서 즉시 재활용할 지식 자산으로 전환하는 것**입니다. RAG가 질문 시점의 검색·생성 층이라면, LLM Wiki는 그 앞뒤에 지속적인 작성·수정·연결·검증의 수명주기를 부여합니다.

## 3. LLM Wiki 아키텍처가 제공하는 실질적 가치

구현 방식을 평가할 때 기능 항목의 개수만 늘어놓으면 핵심을 놓칩니다. 실질적인 도입 이유는 **기존 RAG 구조가 가진 어떤 병목과 구조적 한계를 해소하는가**에서 찾아야 합니다.

### 유연성: 특정 저장소에 갇히지 않는 구조

카파시의 구상은 특정 벤더의 데이터베이스나 벡터 인덱스에 의존하지 않습니다. 사용자는 자신의 목적에 맞춰 폴더 구조, 파일명, 양방향 링크 규칙을 자유롭게 커스텀할 수 있습니다.

이 유연함이 실질적인 차이를 만드는 계기는 지식 구조에 오류가 생겼을 때 나타납니다. 파이프라인 전체를 처음부터 다시 재buid하는 대신, Markdown 문서와 연결 규칙만 수정하면 즉시 바로잡을 수 있습니다. 지식 정본을 사람이 언제든 읽고 편집할 수 있는 파일 형태로 유지한다는 점이 핵심입니다.

### 편집 가능성: 답변을 기억이 아닌 검토 대상으로 바꾸기

RAG의 검색 결과는 매 질의마다 조립되었다가 사라지는 휘발성 문맥입니다. 반면 Wiki 페이지는 사람이 직접 읽고 고칠 수 있는 영속적 자산입니다. 모델이 잘못 이해한 오개념을 교정하고, 빠진 반례를 보완하며, 특정 조건에서만 유효한 예외 조항을 명시적으로 덧붙일 수 있습니다.

따라서 LLM Wiki의 장점은 모델의 단기 기억력에 의존하는 것이 아닙니다. **무엇을 검증된 지식으로 승격할지 사람이 직접 검토하고 제어할 수 있다**는 점이 실질적 이점입니다.

### 에이전트 친화성: 파일 조작 중심의 낮은 도입 장벽

에이전트는 이미 파일 읽기, 쓰기, 경로 변경, 링크 생성 등 기본 I/O 동작에 최적화되어 있습니다. 복잡한 인프라나 전용 DB 없이도 `raw/`, `wiki/`, `SCHEMA.md` 세 가지 요소만으로 최소 루프를 곧바로 구축할 수 있습니다.

다만 시작이 용이하다고 해서 운영의 정교함까지 저절로 확보되지는 않습니다. 명확한 지침(Harness) 없이 파일 작성만 맡기면, 에이전트는 파편화되고 상충하는 문서를 방치하게 됩니다.

### 속도와 정확도: 지식 범위와 하네스가 결정하는 품질

도메인 경계가 명확한 영역에서는 텍스트 파일과 직관적인 색인 구조만으로도 충분히 빠른 응답 속도를 얻을 수 있습니다. 정확도 역시 단일 임베딩 성능보다는 문서 간 양방향 링크, 출처 명시, 무결성 검증(Lint) 하네스가 얼마나 정교하게 설계되어 있는지에 좌우됩니다.

> 명확한 도메인 경계와 촘촘한 하네스가 결합될 때, LLM Wiki는 반복 질의에서 뛰어난 응답 속도와 안정적인 정확도를 보여줍니다.

### 비용 구조의 재해석: 토큰 소모에서 지식 자산으로의 전환

LLM Wiki 도입에는 비용이 따릅니다. 원문을 읽고, 기존 페이지와 비교하며, Wiki를 갱신하고, 질의 시 관련 노트를 다시 참조하는 과정에서 지속적인 토큰 소모가 발생합니다. 종량제 API 환경에서는 단발성 RAG 질의보다 초기 토큰 소모가 큽니다.

하지만 일정량의 사용량이 포함된 구독제 환경이거나 지식 재사용성이 높은 도메인이라면 계산이 달라집니다. 일회성 대화로 소모되어 사라질 토큰을 **다음 질의에서 재활용할 영속적 지식 파일로 변환하는 전략적 투자**가 되기 때문입니다.

```text
RAG       = 질문시마다 검색 → 문맥 조립 → 일회성 답변 생성 (비용 매번 반복)
LLM Wiki  = 원문 Ingest → Wiki 갱신 → 지속 지식 구축 → 효율적 질의 응답
```

결국 LLM Wiki는 RAG를 밀어내는 기술이 아니라, RAG가 찾아낸 원문과 판단 결과를 **지속 가능한 지식 자산으로 승격시키는 정제 계층**입니다.

## 4. 최소 구조를 이루는 세 가지 층

카파시의 원형 구상은 LLM Wiki의 최소 구조를 아래 세 층으로 간결하게 정립합니다.

![변경하지 않는 Raw Sources, LLM이 유지하는 Markdown Wiki, 작업 규칙을 담은 Schema의 세 층](../../attachments/llm-wiki-origin-and-implementations/llm-wiki-origin-and-implementations-figure-01.png)

### Raw Sources

논문, 기사, 보고서, 이미지 등 수집된 원본 데이터 보관소입니다. 사람은 최신 원자료를 선별해 집어넣고, LLM은 이를 참조하되 원본 파일 자체는 수정하지 않습니다. 모든 Wiki 문서의 근거가 되는 불변의 기준점(Ground Truth) 역할을 수행합니다.

### Wiki

LLM이 생성하고 지속적으로 수정·보완하는 Markdown 문서 집합입니다. 단순 요약집이 아니라 여러 원자료 간의 관계를 교차 편집한 **지속적 지식 산출물**입니다.

### Schema

에이전트가 Wiki 구조를 어떻게 생성하고 유지해야 하는지 규정하는 작업 지침서입니다. 파일 명명 규칙, 링크 체계, Ingest·Query·Lint 수행 절차와 도메인 제약 조건을 명시합니다.

에이전트에게 단순 요약을 지시하는 것만으로는 체계적인 구조가 유지되지 않습니다. 어느 시점에 신규 문서를 생성하고, 언제 기존 문서에 통합할지 Schema를 통해 제어해야 합니다.

```text
llm-wiki/
├── raw/          # 원자료 보관소 (Unmutated)
├── wiki/         # LLM이 관리하는 Markdown 지식고 (Mutable)
│   ├── index.md
│   └── log.md
└── SCHEMA.md     # 에이전트 작업 지침 및 구조 계약
```

## 5. Wiki를 지탱하는 3가지 순환 프로세스

### Ingest — 새 원문의 지식 통합

새로운 원자료가 `raw/`에 추가되면 에이전트는 다음과 같은 단계로 지식을 통합합니다.

1. 원문 데이터를 분석합니다.
2. 기존 `index.md`를 조회해 관련된 기존 문서를 탐색합니다.
3. 신규 Source 또는 Summary 문서를 생성합니다.
4. 연관된 기존 개념·인물·주제 문서를 업데이트합니다.
5. 문서 간 양방향 링크를 연결합니다.
6. 색인 파일과 작업 로그(`log.md`)를 갱신합니다.

단순히 개별 요약 파일을 쌓는 것이 아니라, 새 정보가 들어올 때 기존 지식과의 관계망을 전체적으로 재구성한다는 점이 핵심입니다.

### Query — 맥락 기반 질의 응답

질문이 입력되면 에이전트는 전체 문서를 매번 처음부터 읽지 않습니다. 색인 문서에서 관련 주제를 1차 식별하고, 해당 지식 노트를 참조하여 답을 도출합니다. 세부 사실 검증이 필요할 때만 Raw Source로 역추적합니다.

이 과정에서 도출된 고차원적 비교나 종합 분석 결과는 일회성 답변에 그치지 않고 신규 Synthesis 문서로 승격시켜 다시 저장할 수 있습니다.

### Lint — 지식 기반의 무결성 검증

Wiki가 확장될수록 다음과 같은 구조적 결함이 발생할 위험이 커집니다.

- 연결이 끊어진 고아(Orphan) 페이지
- 존재하지 않는 대상을 가리키는 고장 난 링크
- 색인에서 누락된 문서
- 상충하는 정보나 정합성 오류
- 원문 업데이트가 반영되지 않은 노후화된 지식

Lint 프로세스는 단순 오탈자 체크를 넘어, 지식 네트워크의 건강 상태를 지속적으로 진단하고 교정하는 무결성 유지보수 작업입니다.

## 6. 대표적인 구현 경로와 확장 패턴

동일한 원형 구상에서 출발했지만, 프로젝트가 집중하는 레이어에 따라 다채로운 형태 구현체로 발전했습니다.

![같은 원문 계약을 Agent Skill·CLI·Obsidian·Compiler·DocTology라는 여러 구현 경로로 구체화한 비교 지도](../../attachments/llm-wiki-origin-and-implementations/llm-wiki-origin-and-implementations-figure-02-v2.png)

### 6.1 Agent Skill / Plugin — 에이전트 행동 계약 중심 구현

[praneybehl/llm-wiki-plugin](https://github.com/praneybehl/llm-wiki-plugin)은 원문의 구조를 에이전트가 따르는 스킬과 플러그인 형태로 이식했습니다. 코딩 에이전트 환경에 곧바로 적용할 수 있어 원형에 가장 가깝지만, 에이전트가 Schema 지침을 얼마나 엄격히 준수하느냐에 따라 품질 편차가 생길 수 있습니다.

### 6.2 CLI — 명시적 작업과 승인 절차 구체화

[hellohejinyu/llm-wiki](https://github.com/hellohejinyu/llm-wiki)는 `init`, `ingest`, `query`, `lint` 등 명령줄 인터페이스를 통해 지식 갱신을 제어합니다. AI의 파일 변경 사항을 즉시 반영하지 않고 제안(Diff) 상태로 제시하여 사용자 승인을 거치게 함으로써 안전성을 높였습니다.

### 6.3 Obsidian Plugin — 사람 중심의 시각적 탐색 환경

[green-dalii/obsidian-llm-wiki](https://github.com/green-dalii/obsidian-llm-wiki)는 Obsidian 환경 내에서 그래프 뷰와 양방향 링크를 활용해 사람의 직관적인 탐색과 편집 경험을 극대화한 구현체입니다.

### 6.4 Compiler — 엔터프라이즈 운영 기능 확장

[atomicstrata/llm-wiki-compiler](https://github.com/atomicstrata/llm-wiki-compiler)는 출처 추적(Provenance), 검토 대기열(Review Queue), 하이브리드 검색(BM25+Vector+Graph) 등 실무 운영에 필요한 고급 기능들을 엔터프라이즈 레벨로 확장한 스택입니다.

### 6.5 DocTology — AGENTS.md를 통한 하네스 규격화

[DocTology](https://github.com/tteggu87/DocTology)는 저장소 레벨의 `AGENTS.md`를 핵심 하네스로 삼아 에이전트의 작업 경로와 무결성 검사를 자동화한 실전 적용 사례입니다.

## 7. 공통 핵심 규약과 개별 확장 레이어

구현체의 가치를 평가할 때 단순히 기능의 개수만 세어서는 안 됩니다. 카파시 원문이 정의한 **공통 핵심 규약**과 개별 프로젝트가 추가한 **어댑터·확장 레이어**를 구분해서 바라봐야 합니다.

![원문 핵심, 구현 어댑터, 운영 확장을 분리해 읽는 LLM Wiki 비교 원칙](../../attachments/llm-wiki-origin-and-implementations/llm-wiki-origin-and-implementations-figure-03.png)

```text
카파시 원형 구상
  ├─ 핵심 규약: Raw / Wiki / Schema 3층 구조 + Ingest / Query / Lint 3대 작업
  ├─ 접점 어댑터: Agent Skill / CLI / Obsidian UI / AGENTS.md 규약
  └─ 운영 확장: Provenance 추적 / 검토 대기열 / 하이브리드 검색 / MCP 연동
```

## 8. 적합한 유즈케이스와 채택 판단 기준

LLM Wiki가 모든 상황에서 전능한 해법은 아닙니다.

- 단순 일회성 단발 질의
- 실시간으로 급변하는 외부 정보 확인
- 지식 유지 비용이 재활용 가치보다 큰 소모성 작업

위와 같은 유즈케이스에서는 일반적인 RAG나 단순 파일 검색이 훨씬 효율적입니다.

반면 **여러 자료를 장기적으로 비교 분석하고, 이전의 판단과 실패 사례를 지속적으로 재활용해야 하며, 사람이 직접 지식의 정합성을 검토하고자 할 때** LLM Wiki 도입의 실질적 이점이 발생합니다.

결국 가장 가벼운 구조로 먼저 시작하여 지식 재활용률과 생산성 변화를 직접 측정한 뒤, 필요에 따라 검색 인덱스나 온톨로지 레이어를 단계적으로 확장해 나가는 것이 바람직합니다.

## 9. 후속 분석을 위한 5가지 비교 축

Agent Skill, CLI, Obsidian Plugin, Compiler, DocTology `wiki-only` 프로필을 종합적으로 평가할 때 적용되는 5가지 관점입니다.

- 원자료와 생성 Wiki의 구조적 격리도
- Schema 및 `AGENTS.md` 규약 준수율
- Ingest·Query·Lint 실제 동작 특성
- 인간 승인 및 개입 메커니즘
- Provenance 및 검색 레이어 확장성
